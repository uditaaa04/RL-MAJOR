Three checkers, one box

The gateway's webcam photographs every box. Three programs can judge the photo. The gateway's model looks first, in about 2 ms. If it is unsure, the agent can also ask the cloud for a second opinion. If the cloud answers too late, the gateway's verdict is used, so the box is still checked.

  • Tiny model on the ESP32. The board that runs the belt. It gets a shrunken grey photo over the USB cable. Weakest eyes, used only when the laptop is too busy to check boxes in time.
  • Small model on the gateway laptop. Right next to the belt, fast, good accuracy, unless the laptop is busy.
  • Big model on the cloud server. Most accurate, but the photo has to travel there and back.

A race against the belt

The box keeps moving. From the camera to the reject arm it travels for about 0.3 to 0.7 seconds. That is all the time there is.

An answer that arrives after the box has passed the arm is worthless. The box ships unchecked, which is the worst outcome on this line. So a weak answer in time beats a perfect answer too late.

How it scores itself

After every box it gets a score. The score is a cost, so closer to zero is better.

  • A damaged box is shipped100
  • A box passes uncheckedabout 35
  • A good box is thrown away10
  • Electricity used1 per joule

For each situation it keeps three numbers: the score it expects from keeping the gateway's verdict, from asking the cloud, and from the ESP32. It picks the best one, sees what happened, and corrects the number. That is Q-learning. Cloud calls are limited, so a call spent on an easy box is missing for a hard one a few boxes later; the agent learns that too.

Spot checks. What a cloud answer is worth was first measured on the training photos. A real line drifts away from those: a lamp fails, the belt runs faster and the photo smears. So whenever the true state of a box is known afterwards (a test run with a known box order, or a person checks some boxes), the agent compares the gateway's and the cloud's verdict on that box and keeps its own tally per confidence level. The tally replaces the old number. The map on the Live page shows both.

Why learn, instead of writing a rule

A hand-written rule has thresholds. Someone must tune them again every time the Wi-Fi, the belt speed or the server changes. The agent re-tunes itself from the results it gets.

Ping cannot see an overloaded server or a capped connection: a tiny ping packet still flies through. The 2-second test photo can. A rule that trusts ping misses half or all of the boxes in those faults.

A rule can also send only the unsure boxes to the cloud. But how unsure is unsure enough depends on the network, the time left and the calls left. The agent learns that from results.

It first practises on 2.4 million simulated boxes, each one a real photo, then keeps learning on the real belt.

What is proven, and what is not

  • Done. Complete system, strong hand-written rule to compare against, every result re-runnable.
  • Done. In simulation it matches or beats that rule on average, and recovers by itself from faults it never saw.
  • Not yet. Results on the real belt. Until then every decision result is simulated.
  • Not yet. ESP32 speed measured on the real board. Until then its time is an estimate.
  • Not yet. Models trained on real photos. The shipped ones learned from computer-drawn boxes.
  • Not claimed. That the idea is new. Offloading with Q-learning is well known. The contribution is the deadline-driven, cost-based design and the test against a strong rule.
